## BUG-001 金额三位小数可提交，落库静默四舍五入

- **模块**：账单 / 订单金额　**严重**：P1（账目对不上，属于资金类问题）
- **前置**：采购部账号；新建账单页
- **复现**：
  1. 新建账单，金额填 `12.345`
  2. 保存
  3. 重新打开该账单，对比列表页的金额与详情页的金额
- **预期**：要么前端拦住"最多两位小数"，要么落库后各处显示一致
- **实际**：提交成功；库表 `decimal(20,2)` 按四舍五入存 `12.35`，页面输入框/明细页仍显示原输入或另有舍入结果，出现分位差
- **根因**：`src/main/webapp/WEB-INF/jsp/footer.jsp` 的表单校验只有 `isNaN(parseFloat(v))`（"是不是数字"），**没有小数位与范围校验**；`dsscm.sql` 里 `totalPrice / cost / productCount` 都是 `decimal(20,2)` / `decimal(10,2)`，精度超出的部分由 MySQL 静默处理
- **修复方案**：① 前端限制输入两位小数并给出提示；② 后端接收时统一 `BigDecimal.setScale(2, RoundingMode.HALF_UP)`，不依赖数据库隐式舍入；③ 金额合计一律在服务端用 `BigDecimal` 计算，不在页面用 JS 浮点累加
- **回归**：TC-SC-11 / TC-SC-12 / TC-SC-14

> 这条的价值不在"发现了个小数位问题"，而在**定位链路**：从"账面金额对不上"→ 查页面校验 → 查库表精度 → 查服务端是否用 `BigDecimal`。面试被问"你怎么定位金额精度问题"，就按这个顺序讲，比背概念有用。

## BUG-002 修改类申请被驳回后，业务记录状态未回退

- **模块**：审批流　**严重**：P1（单据卡死：既不能在原记录上继续编辑，也不会自动恢复原状态）
- **前置**：一条已存在的账单/商品/供应商记录；经理账号
- **复现**：
  1. 对某条已有账单提交一次「修改」申请（`action=update`）
  2. 业务记录被置为 `approvalStatus=1 待审批`
  3. 经理在审批台点「驳回」
  4. 回到该账单列表，查看记录状态与可编辑性
- **预期**：驳回后业务记录回到驳回前的状态（已通过），用户可以重新提交修改；页面上应能看出"上一次修改被驳回"的原因
- **实际**：业务记录停在 `approvalStatus=3 已驳回`，既不是"已通过"，也不在"草稿"里，编辑入口按状态过滤后不可用；原值其实还在库里，但用户从界面进不去
- **根因**：`ApprovalServiceImpl#reject` 对非 `add` 动作只做了 `updateBusinessStatus(module, recordId, 3)`（置驳回），**没有保存驳回前的状态、也没有回退动作**；`tb_approval` 一张表承担"申请单"，业务表只有最终态字段，缺少"当前状态 + 上一状态"的历史
- **修复方案**：① 业务表加 `previous_status`，提交修改申请时记录、驳回时回退；② 或在审批通过/驳回时以 `tb_approval` 为唯一事实源，业务表的 `approvalStatus` 只作派生展示，避免两处状态各写一半
- **回归**：TC-SC-03 / TC-SC-09

## 观察清单（未定性，不当缺陷）

| 编号 | 现象 | 为什么先不定性 | 怎么定论 |
|---|---|---|---|
| OBS-01 | `apply()` 对 `status != 0` 的申请直接 `return`，接口仍旧返回 `"ok"` | 是否算缺陷取决于接口约定：如果前端只按返回值提示"成功"，就是假成功；如果前端另查状态，则影响有限 | 连点两次「通过」，看页面提示与 `tb_approval` 是否只有一条被处理（TC-SC-04） |
| OBS-02 | `canApprove()` 只判角色（ADMIN/MANAGER），不判"是否本人提交" | 小团队里经理自己提自己批可能是有意允许 | 确认业务规则后决定是否拦截（TC-SC-06） |
| OBS-03 | `executeApproved()` 里 `detailJson` 解析失败时没有兜底反馈（异常被吞，状态已经改成"已通过"） | 需要构造一条字段不匹配的 JSON 才能复现 | 手工改一条 `detailJson`（少一个字段）再审批，看是否"通过但没改数据"（TC-SC-10） |
